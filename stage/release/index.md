# 发布

发布阶段把已经构建、测试并审计通过的提交变成可被他人获取的版本。

本章分为两部分：

- [发布执行](publish.md) — 说明如何选择 CLI 发布或手动操作路径
- [发布审计](audit.md) — 说明发布前、发布中、发布后的检查方法

## 决策顺序

发布前先按以下顺序判断：

1. 识别发布对象：确认是根仓库发布，还是 `cli`、`provider`、`studio` 等 scope 发布。
2. 识别发布目标：确认是否发布到 GitHub Release、crates.io、PyPI、npm、pub.dev、容器镜像仓库、内部制品库，或仅做版本记录。
3. 识别发布入口：项目已接入 `qtcloud-devops` 或发布 CI 时，默认使用 CLI 触发；没有自动化能力时才进入手动操作。
4. 执行发布前审计：版本、CHANGELOG、工作区、构建、测试、凭证和安全检查都通过后再发布。
5. 执行发布并留存证据：记录 tag、Release、registry、CI run、二进制资产或内部制品地址。
6. 执行发布后审计：确认所有声明的发布目标都可访问、版本一致、安装或下载路径可用。

## 管理员与 AI 的分工

管理员负责确认发布意图：发布哪个 scope、发哪个版本、面向哪些使用者、是否允许手动备用路径。

AI 负责对照事实源做一致性检查：读取配置文件、CHANGELOG、Git tag、CI workflow、制品库配置和发布日志，指出缺口并给出下一步操作。AI 不应在事实源不足时替人断言“已经发布成功”。

当管理员意图与仓库事实冲突时，以仓库事实为准，先修复事实源，再执行发布。
